# Requirements Traceability Matrix (RTM)

The RTM traces requirements from their originating stakeholder need or source through the requirement itself, to the acceptance criteria. The RTM is structured so that later evidence can be added without rebuilding it. The full expected chain runs as follows:

**Stakeholder/Source → Requirement → Design/Architecture → Issue/PR → Implementation → Test → Acceptance/Release Evidence**

In the table below, the Source, Requirement and Acceptance Criteria portions of the chain are established. Final status for release v4.0.0 (updated 18/10/2026 against main, RTM curator: Donya). The Test Ref column lists the test IDs as they appear in the test code (TC-E = Elcke, TC-A = Adolf, TC-D = Donya; INT = API/integration, E2E = end to end). Section 2 (Test reference key) names the test class behind every ID and maps the code TC-E IDs to the numbers used in the status-lifecycle evidence file. The Status column keeps "implemented" and "verified" apart and names the level of evidence (Section 1). Open defects and gaps that affect an acceptance criterion are named in the Status column. Once a requirement is baselined, it cannot be changed without an approved change record. Maintaining structured traceability is a recognised and consistent challenge in software engineering practice (Mucha, Kaufmann & Riehle, 2024); for this reason, the RTM is treated as a live artefact from this milestone onward.

## 1. Status and evidence levels

Status values:
* **Verified (automated):** an automated test checks the acceptance criterion.
* **Verified (manual):** checked by hand on a recorded date; no automated test.
* **Verified (automated + manual):** both, as listed in Verification Evidence.
* **Implemented; criterion verified manually only:** the code is tested, but the acceptance criterion itself is only shown by hand.
* **Partly verified:** part of the criterion is tested automatically; the named part is not.
* **Implemented — not verified (test gap):** the code exists, but no test checks the criterion.

Evidence levels used in the Verification Evidence column. They are not equal, and the RTM does not treat them as equal:
* **Manual check:** a person checks the behaviour on a recorded date (live check 14/10, timed demo 18/10, 375 px recheck 18/10).
* **Unit or service test with mocks:** checks the logic of one class; no database or web layer (Mockito or plain JUnit).
* **API integration test on H2:** starts the full Spring app with an in-memory H2 database in PostgreSQL mode and calls the real API (@SpringBootTest).
* **Frontend unit test:** checks frontend logic with node --test; no browser.
* **E2E on simulated staging:** Playwright drives the running app (local Vite + Spring).
* **Automated PostgreSQL test:** none in this release. PostgreSQL-only behaviour (the V2 append-only triggers) is checked by hand (TD-006).

Open test gaps at release: NFR002 (RTM-015) has no test; NFR004 (RTM-017) has no automated test of the PostgreSQL trigger; FR004/NFR001 (RTM-004, RTM-014) have no automated timing test.
